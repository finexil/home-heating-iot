# Extra Heating Algorithm – Smart Photovoltaic Surplus Routing

🇮🇹 *Per la versione in italiano, clicca [qui](extra_heating.it.md).*

The **Extra Heating** algorithm enables the system to intelligently harness excess electrical power generated by the home's photovoltaic (PV) array. By redirecting this surplus energy into the thermal mass of the house **when it is most cost-effective**, the system minimizes overall grid consumption and raises thermal comfort.

As one of the most innovative architectural components of this project, it dynamically orchestrates:
* ✅ Real-time home electrical metrics and grid parameters.
* ✅ Distributed thermal logic inputs calculated at the thermostat edge.
* ✅ Strict room-by-room environmental safety limits (maximum 22°C ceiling).
* ✅ Real-world hydronic system behaviors (slab thermal inertia, mechanical deployment lag, and short-cycling prevention).
* ✅ Seasonal constraints and optimized operational timeframes.

---

## 1. Algorithmic Objectives

The Extra Heating loop is engineered to satisfy the following criteria:
* Consume **surplus** solar generation locally at zero additional running utility cost.
* Pre-heat the building wrapper structural framework **only when thermodynamic conditions are favorable**.
* Honor the maximum defined user comfort temperature thresholds.
* Restrict execution exclusively to high-irradiance daytime hours.
* Guarantee zero energy waste if the building envelope already matches peak thermal storage capacity.
* Suppress short-cycling behavior that leads to premature mechanical wear on pumps and relays.

---

## 2. Activation Pre-requisites

The Extra Heating routine switches into an active state **if and only if all the following conditions evaluate to true**:
* ✅ Real-time PV generation breaks the minimum configured power output threshold.
* ✅ The domestic battery bank state of charge (SoC) is verified full or operating inside a high-surplus profile.
* ✅ Active household net power load < live array generation (confirming real net solar surplus).
* ✅ The current time falls within the daily high-irradiance execution frame (e.g., **09:30 – 16:30**).
* ✅ The current month falls within the local heating season envelope (typically **October to March**).
* ✅ At least one independent structural zone tracks below the safety threshold of **22°C**.

> ⚠️ If any single boundary constraint fails validation, the Extra Heating state remains completely disabled.

## 3. Data Ingestion Matrices

The background script regularly pulls variables from three functional boundaries:

### 3.1 Energy Metrics Layer (via SolarEdge API or local sensor clusters)
* Real-time photovoltaic power output.
* Home storage battery charge/discharge vectors.
* Total real-time house power consumption.
* Calculated net active generation surplus (\(P_{\text{PV}} - P_{\text{Load}}\)).

### 3.2 Thermal Telemetry Layer
* Indoor environmental temperature charts parsed via the `termostat_temp_now` cache table.
* Outdoor micro-climate trends monitored through the `external_temp_hum_now` row.
* Active call-for-heat constraints established by room terminals.
* Mechanical manifold configurations verified within the `zone_status` table.

### 3.3 Plant Physical Infrastructure State
* Active biomass hybrid thermo-stove status flags.
* Boiler burner relay and manifold distribution pump records from `heating_state`.
* Real-time system calendar clock and active month metrics.

## 4. Optimization Activation Sequence

When all boundary pre-requisites are verified, the core automation engine shifts operational parameters:

### 4.1 Global Thermostat Force Mode
The script updates the `termostatSetup` schema configuration table, forcing the solar optimization flag `f0 = 1` across all managed heating zones. Local room thermostat terminals capture this flag change during their polling routine and immediately insert an assertive call row (`1`) into the `termostat_warming_request` ledger.

### 4.2 Room-Level Temperature Veto (22°C Ceiling)
If an individual space crosses the strict **22°C ceiling**, the local thermostat edge client:
* Bypasses the global force constraint.
* Drops its specific zone call indicator back to idle (`0`).
* Maintains standard time-series data aggregation pushes to `powerDetails`.

This safety feature acts as a fundamental defense against room overheating and energy wastage.

### 4.3 Plant Mechanical Fire Sequence
The manifold actuator microcontrollers scan the cached states inside the `termostat_warming_request` lookup view, open the active zone electrovalves, and log the deployment step by setting the zone column to `1` within the `zone_status` matrix. 

The primary boiler logic engine evaluates the active columns inside `zone_status`. If at least one zone reports a successfully opened position (`1`), it runs the plant circulation pumps, follows up with the protective **90-second delay loop**, and fires the burner relays.

---

## 5. Optimization Deactivation Sequence

The Extra Heating algorithm drops out of service and returns parameters to standard operations as soon as any of the following transitions occur:
* The photovoltaic net solar surplus drops below the active threshold.
* The system clock exits the optimization time frame.
* The system transitions into an unmapped calendar month.
* Every managed zone successfully warms past the **22°C threshold**.
* The biomass hybrid thermo-stove node changes state to active (`stove_on = 1`).

Upon deactivation, the central automation server writes `f0 = 0` across all zones in `termostatSetup`, returning the home to normal schedule profiles.

## 7. The 22°C Core Principle: Comfort & Efficiency

The design requirement of the Extra Heating cycle is **not to overheat the living spaces**, but rather to:
* Stabilize ambient interior temperature drift curves.
* Capitalize on zero-cost, localized renewable energy assets.
* Counteract the significant lag characteristics of hydronic floor structures by pre-charging the floor mass.

Enforcing the 22°C maximum ceiling avoids interior discomfort, eliminates power waste, isolates individual zone behaviors, and stops the primary plant from executing unproductive burn sequences.

---

## 8. Subsystem Logic Interlocking

### 8.1 Biomass Hybrid Thermo-Stove
If the wood stove fires up (`stove_on = 1`), the system priority matrix shifts flow logic entirely onto the biomass loop. The Extra Heating framework remains online but steps aside to allow the zero-cost wood loop to balance structural loads, preventing energy resource conflicts.

### 8.2 Boiler Logic Controller
The automated system applies identical verification steps to safeguard the hardware components. The heat pump only fires if a real structural load is confirmed, shielding the compressor relays from consecutive short-cycle activations.

### 8.3 Manifold Valve Actuators
The Extra Heating algorithm pushes system-wide zone requests, but the physical actuators only deploy loops for spaces currently sitting below the 22°C boundary. This safeguards the home from wasting pump capacity on rooms that are already fully saturated with heat.

## 9. Audit Logging & System Diagnostics

Every operational transition is recorded inside the central database layer using explicit diagnostic strings:
* `heating_state.reason = 'EXTRA HEATING ON'`
* `heating_state.reason = 'EXTRA HEATING OFF'`

Each log row appends system variables including execution timestamps, net PV solar surplus wattage, real-time internal temperature vectors, outdoor micro-climate contexts, and active manifold positions. This time-series tracking ledger provides the data baseline needed to optimize future automation routines.
