# Compact Thermostat – ESP8266 Firmware Reference

🇮🇹 *Per la versione in italiano, clicca [qui](thermostat_esp8266.it.md).*

This document describes the embedded firmware logic, structure, and operational cycle running on the **ESP8266 (ESP-12E module)** array coupled with a **1.8" TFT display**.

Deployed across secondary bedrooms and bathrooms, this peripheral serves as the specialized "compact" form factor of the home automation ecosystem's core climate sensing grid.

---

## 1. Algorithmic System Architecture

The peripheral firmware targets the following programmatic criteria:
*   ✅ Periodically samples ambient temperature and relative humidity metrics.
*   ✅ Evaluates the dynamic zone schedule configurations retrieved from the storage layer.
*   ✅ Processes hardware external interrupts generated by physical tactile navigation buttons (`PAGE_SELECT` and `WARM_FORCE`).
*   ✅ Renders historical trend charts and context-driven status graphics.
*   ✅ Pushes a 10-minute calculated rolling average dataset to the central MariaDB backend.
*   ✅ Dispatches immediate, event-driven network transactions as soon as local zone state shifts occur.

The code base is structurally engineered to be exceptionally **robust**, **responsive**, and simple to update over the local network.

---

## 2. Hardware Interface Specifications

### 2.1 Component Architecture
*   **Edge MCU Core:** ESP8266 Espressif ESP-12E platform.
*   **Display Layer:** 1.8" SPI TFT display panel (driven by the ST7735 matrix controller).
*   **Sensory Array:** DHT22 high-precision environmental sensor framework.
*   **User Navigation Input:** Dual physical button layout configurations mapped to active pull-down circuits:
    *   **`PAGE_SELECT`** (Navigates display pages).
    *   **`WARM_FORCE`** (Imposes manual user overrides).
*   **Power Circuit Isolation:** Centralized 5Vdc bus input regulated down to a stable 3.3Vdc via a dedicated AMS1117 low-dropout (LDO) regulator.

## 3. Firmware Execution Lifecycle

The edge controller runs a sequential state machine utilizing cooperative, non-blocking timing blocks (`millis()`-based execution loops):

```text
MAIN FIRMWARE LOGIC LOOP (Every 5 Seconds)
 ├──> Sample digital DHT22 environmental sensor lines
 ├──> Calculate and append metrics to the 10-minute rolling average buffer
 ├──> Flush screen buffer to update display (Telemetries, Icons, Mini-Charts)
 ├──> Evaluate active WARM_STATE parameters against WARM_FORCE overrides
 ├──> IF (Calculated Request Vector shifts vs. Previous Interval):
 │     └──> Spawn immediate SQL transaction to write state mutations to DB
 └──> IF (Continuous 10-Minute Timer Interval expires):
       └──> Spawn direct SQL transaction to append rolling data frames to DB
```

This cooperative design ensures:
*   ✅ High edge-device loop responsiveness.
*   ✅ Reduced low-power operational thermal dissipation.
*   ✅ High local Wi-Fi transceiver stability.
*   ✅ Minimized query transaction overhead targeting the central single-board server.

## 4. Control Directives: WARM_STATE and WARM_FORCE

### 🔶 `WARM_STATE`
Represents the target hourly calendar constraint fetched directly from the Raspberry Pi core:
*   `0` — Thermal delivery idle (Zone Schedule Standby).
*   `1` — Active heating required (Zone Schedule Demand).

This parameter payload is retrieved asynchronously from the network endpoint every few minutes.

---

### 🔶 `WARM_FORCE`
Coordinates the state transitions generated when a user hits the physical tactile override button:
*   `0 = NORMAL` (The terminal ignores manual intervention and tracks the automated `WARM_STATE` scheduler curve).
*   `1 = FORCE ON` (Forces immediate, unmetered hot water delivery across the hydronic loop).
*   `2 = FORCE OFF` (Locks out the heating loop entirely, ignoring temperature rules).

The absolute calculated decision variable pushed to the transaction database follows this rule:

```text
Computed Zone Request =
    IF (WARM_FORCE == FORCE OFF) ──> Return 0
    IF (WARM_FORCE == FORCE ON)  ──> Return 1
    IF (WARM_FORCE == NORMAL)     ──> Return WARM_STATE
```

## 5. Direct MySQL/MariaDB Core Driver Layer

The firmware establishes native network connections directly targeting the centralized backend server via the direct `MySQL_MariaDB_Generic` driver framework to run raw execution commands.

### 🔍 5.1 Pushing Environmental Telemetry (Table: `powerDetails`)
Executed exactly on a 10-minute structural interval:
```sql
INSERT INTO temperature.powerDetails (room, Temperature, Humidity, Pressure) 
VALUES ('%s', %.3f, %.3f, 0.0);
```
*(Parameters inject the mapped `room_id` string, calculated temperature float, relative humidity float, and a static zero placeholder for barometric values).*

### 🔍 5.2 Dispatched Event Transactions (Table: `Warming_state`)
```sql
INSERT INTO temperature.Warming_state (room, FLG_ON, FLG_FORCE) 
VALUES ('%s', %d, %d);
```

### 🔍 5.3 Fetching Zone Profiles & Optimization Flags (Table: `TermostatSetup`)
```sql
SELECT * FROM temperature.TermostatSetup 
WHERE room='%s';
```
*Retrieves the room's targeted scheduler mapping along with the dynamic solar optimization bit (`f0`) and the biomass priority flag (`f1`).*

## 7. Tactile Button Navigation Management

### ▶️ `PAGE_SELECT` Tactical Switch Interrupt
Cycles through the three visual dashboard layouts. Debouncing is handled purely in software via timestamp checks to block mechanical bounce noise.

### 🔥 `WARM_FORCE` Override Tactical Switch Interrupt
Cycles the manual override variable through its states: `NORMAL ──> FORCE ON ──> FORCE OFF`. Every physical button press triggers an immediate event-driven database push, bypassing standard waiting intervals.

## 8. Fault Tolerance & Hardened System Safeties

The compact firmware architecture integrates the following protection matrices:
*   Granular Wi-Fi socket connection drop timeout retry windows.
*   Automated emergency hardware resets driven by native ESP8266 Watchdog Timers (WDT) to clear potential thread lockups.
*   Wi-Fi non-blocking background re-authentication parameters.
*   Continuous digital bus error auditing mapping DHT22 line states.
*   **Telemetry Failure Fallback:** If the local sensor encounters a hardware fault or returns an invalid readout, the code locks onto the **absolute last verified safe value** to maintain system operation while streaming warning flags to the database server.
